# Adversarial Review — Spec-Yard MVP PRD

- **Reviewed:** `prd.md` (+ companion `addendum.md`), 2026-07-08
- **Method:** Cynical Review per `bmad-review-adversarial-general`
- **Findings:** unranked list, per skill output format

## Findings

- **The PRD and its own addendum describe two different products, and the PRD routes the contradiction downstream unresolved.** PRD §G1: Spec-Yard is "a standalone tool, separate from any target repo," with specs living in a dedicated project folder. Addendum §A (declared in §11 as "the intended input to the design doc"): "specs are plain `*.spec.yaml` files living inside the target project's repo... spec-yard becomes an editor/viewer pointed at those files." Specs-next-to-code vs. specs-in-their-own-folder changes the agent handoff story (UJ2), the PR-review story ("architect reviews spec diffs in the PR" — in *which* repo's PR?), and the file-access security model. The PRD silently reversed the addendum's core premise without recording it as a decision, then blessed the contradicting brief as the design-doc seed. The design doc will inherit a coin-flip.

- **This is not an MVP; it is a v1.0 with the label changed.** Five feature groups, 17 FRs, no priority ordering, no cut line, and release criteria demanding *all* FRs plus all three user journeys demoable. G1 alone is an architectural inversion (persistence layer, file watcher, conflict handling, migration, dual-mode operation). G2 is a schema change + new lint semantics + canvas collapse/expand + edits to three views + simulator roll-up. G3 is a full UX overhaul with onboarding. Any one of these is a release. The obvious staged cut (G1+G5 ship first; G2 follows) is never discussed, so a timeline slip has no planned degradation path — the release criteria make the whole thing all-or-nothing. There are also no dates, milestones, or effort estimates anywhere in the document.

- **G2 piles new load onto the historically fragile subsystem that the #1 counter-metric depends on, and doesn't acknowledge it.** The top counter-metric is "zero spec-corruption incidents" from canvas sync — a subsystem with a documented history of sync-race corruption. FR8–FR11 now require that same bidirectional sync to handle module containment, collapse/expand, interface-anchored edges crossing collapsed boundaries, and per-spec view state, all while preserving NFR1 ("never fabricate ghost components"). The PRD treats G2 as a schema feature; it is primarily a canvas-sync risk multiplier, and the risk register for that is absent.

- **FR3's assumed auto-save and FR4's external-edit rule race each other into exactly the silent clobbering FR4 forbids.** With debounced auto-save on, an agent's on-disk edit can land in the debounce window; the app flushes local state and overwrites the agent's write with no prompt, because from the app's view there were simply "local edits pending." UJ2 makes concurrent agent edits a *primary* flow, so this race is the common case, not a corner. Related unaddressed failure modes: agent writes non-atomically and the watcher reads a half-written file; file deleted/renamed on disk; git branch switch replacing every spec at once; undo after a reload-from-disk resurrecting a stale spec that auto-save then persists. FR4's "prompt to reload or overwrite" covers the one benign case and none of the dangerous ones.

- **FR3 simultaneously mandates auto-save, a dirty-state indicator, and Save-as-explicit-flush — a combination with no coherent semantics.** If edits persist automatically, the dirty indicator is meaningless most of the time and Save flushes nothing. The FR fixes the UI surface (indicator, wired Save button) while punting the semantics that give those elements meaning to the design doc. Requirements should not lock UI affordances before deciding what they indicate.

- **FR9's mandated quick-fix for encapsulation violations is unspecified and, in its most likely form, defeats the feature.** The obvious one-click fix — "expose the targeted member" — converts strict interfaces into a rubber stamp: every violation is one click away from legal, and the interface-bloat *warning* in the same FR is the only thing pushing back. Alternatively, rewiring the connection to an existing exposed member is a semantic design change no linter should make in one click. The PRD requires a quick-fix without stating what a safe one is; "encapsulation as a linted property" collapses to decoration if the fix is expose-on-demand.

- **SM2 (agent-build fidelity ≥ 80%) is unfalsifiable as written and measures the wrong system.** "≥ 80% of components/connections realized as intended" — intended per whom, judged by whom, on what target codebase, with which agent version, and what counts as a component being "realized"? No protocol exists. Worse, the metric is dominated by Claude Code's capability, not by spec quality: a better agent inflates the score with the spec unchanged. As stated, the number can be neither computed nor failed.

- **The whole of §3 is decoratively quantitative: every threshold is an `[ASSUMPTION]`, measurement is "manual/qualitative," and there is no telemetry.** "Quick-fix adoption should stay high" — relative to what baseline? None exists (§2 says current state "blocks real use," i.e., zero real users), "high" is undefined, and with no telemetry (NFR4) adoption isn't observable at all. "Zero spec-corruption incidents" — with no telemetry and no required detection mechanism (round-trip invariants, golden-file CI checks), a silently dropped comment three saves ago is simply never noticed; a zero-incident target without a detection requirement is a wish. And SM1's "≥ 2 abstraction levels" is exactly what FR8 supplies by construction — the metric cannot fail on that axis. SM3/SM4 have no comparator (vs. Mermaid? vs. a whiteboard photo?), so they cannot show the tool beats the status quo it claims to replace.

- **Release criterion 1 is circular via OQ3, and "consciously revised" is an escape hatch that makes it vacuous.** Criterion 1 requires every `[ASSUMPTION]` "confirmed or consciously revised" before release; OQ3 says the metric thresholds can only be calibrated once internal users exist — i.e., after release. Meanwhile any assumption can always be "consciously revised" to match whatever happened, so criterion 1 can never actually block a release. Criterion 3 ("demoable end-to-end by someone other than the author") is similarly weak: a scripted demo passes with a broken product, and it's ambiguous whether UJ2's demo requires a *successful* Claude Code build — if yes, release gates on an external agent's performance; if no, UJ2 was not demoed end-to-end.

- **NFR4 claims "no exfiltration" while the most likely G1 architecture is a localhost file-write server, and that threat is never mentioned.** The addendum's default file-access mechanism is Next API routes that read/write files under a workspace root. A localhost HTTP server with file-write endpoints is reachable by any webpage the user visits (drive-by POSTs to localhost) unless CSRF/origin/auth protections are required — and the PRD requires only path-traversal guards and a root allowlist, which defend against a different attack. A product that ships STRIDE lint rules for its users' architectures did not STRIDE its own file API.

- **The success bar — "internal architects design real systems by choice" — has no named users, no N, and no date.** OQ3 concedes the first internal users aren't identified. An internal MVP with zero committed dogfooders, no adoption target (how many architects, how many real systems, by when), and no timeline is a launch into a void; "by choice" adoption cannot be evaluated against an audience that doesn't exist yet.

- **FR12 ("Zero lying UI") conflicts with FR6's deferred park-or-delete decision and FR5's localStorage-only mode.** Flag-parked mock sign-in scaffolding is still a code path implying a nonexistent capability — the decision FR12 claims to have made is actually deferred to the design doc in FR6. And in FR5's localStorage-only "hosted-preview" mode, what does the status bar show? The "decorative main.spec.yaml" fiction the PRD denounces in §2 reappears in preview mode, and dual-mode persistence roughly doubles the G1 test surface for a scenario (§2: the market is moving *away* from hosted) that contradicts the local-first identity.

- **Collapsed/expanded state persistence (FR10) is a product decision misfiled as a design detail (OQ4).** If collapse state lives in the spec file, UI state pollutes the "single honest contract" and generates diff noise in every PR — directly degrading UJ2's review flow. If it lives in a side config, then picture-state exists outside the spec, and §1's own principle ("structure must live in the spec itself, never only in the picture") demands an explicit line between structural state and view state. OQ4 labels this "needs no product input." It needs exactly product input.

- **The level-counting terminology is inconsistent enough that an implementer will get it wrong.** §1/§5 say "two encapsulation levels"; FR8 says modules "nest two levels deep," yielding root → module → submodule → component (three container tiers, two sealable); SM1 says "≥ 2 abstraction levels"; §8 says "nesting beyond two module levels." Four phrasings, at least two plausible readings. FR8's parenthetical tries to pin it; the rest of the document undoes it. Pick one counting scheme and use it everywhere.

- **NFR5's "without perceptible lag" is not a requirement; it's an adjective.** At the SM1 ceiling (~40 components), every keystroke triggers YAML parse, 40+ lint rules including graph-topology passes, full-flat-graph computation under collapsed modules (FR11), plus diagnostic roll-up. That needs a latency budget (e.g., p95 keystroke→render < 100ms) or it will be "verified" by whoever has the fastest laptop. Note also that NFR5's performance ceiling equals SM1's success ceiling exactly — zero headroom between "works" and "succeeds."

- **Error handling outside FR4 is entirely absent from G1.** No requirements for: corrupt or unparseable spec file on open; write failure (permissions, disk full) and what "atomic writes" degrade to; migration failure mid-export (FR5); project folder on a synced/network volume where file-watching is unreliable (iCloud, Dropbox, NFS); folder discovery cost in large directories; and — pointedly, given this project's own history with parallel sessions — two app instances open on the same project folder. A persistence PRD with one failure mode specified is a happy-path PRD.

- **FR17's machine-readable output is an unspecified contract that CI and agents will build against anyway.** "`[ASSUMPTION]` JSON" with no schema commitment, no distinction between exit codes for parse failure vs. lint errors vs. tool crash, no statement of where the severity threshold is configured (flag? the OQ4 config file?), and no versioning story for CLI-vs-app rule-engine drift (an agent running CLI vX against a workspace on vY). The one deliverable aimed at machines is the least precisely specified.

- **FR2's default-open behavior is unspecified for the non-happy cases.** "`main.spec.yaml` is the default on first open" — and when it's absent? A folder with three spec files and no `main`, an empty new folder (FR15 covers greeting, not file creation semantics), a folder with zero write permission. Also FR13's onboarding tour runs "on a bundled sample spec" — inside the user's project folder (polluting it) or outside any project (contradicting FR1's one-project model)? The G1×G3 interaction is unexamined.

- **FR16 contains "and/or."** "Saved into the project folder (FR7) and/or downloaded" — a requirement with "and/or" is two requirements or none. Pick the behavior (or specify the toggle that selects it).

- **Document hygiene: the PRD's own metadata contradicts its edit history.** OQ1 is marked "Resolved (2026-07-08)" while the frontmatter says `updated: 2026-07-07`. Trivial to fix, but a document whose central pitch is "the spec and the picture are never allowed to drift" should not itself drift from its own changelog. Additionally, "NFR6 — TDD" is a process mandate, not a verifiable product requirement (suite-stays-green is verifiable; "TDD" post-hoc is not), and §2's competitive assertions ride entirely on `discovery-notes.md` — which does exist, but the PRD proper cites no evidence for claims like the Structurizr EOL date.
