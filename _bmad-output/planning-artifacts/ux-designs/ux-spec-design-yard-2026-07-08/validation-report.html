Adversarial review — cynical reviewer

review-adversarial.md 2 critical · 7 high · 12 medium · 3 low

These spines are well-written prose sitting on top of an engine that cannot do several of the things they promise. The two headline gestures — double-click to descend and boundary pins at the canvas edge — fight Excalidraw's own double-click-to-edit and its infinite-canvas coordinate model, and the whole line-jump/syntax-highlight editor story assumes a code editor the app does not have (a bare <textarea>). The "lean default = exactly three things" banner is contradicted three lines later by the doc's own always-present furniture and by four differently-meaning dot/badge status indicators shipping at rest — the exact chrome accretion this product exists to kill. Most of the visual/token discipline is genuinely strong; the danger is concentrated in the behavior spine writing physics the canvas engine can't honor, which is itself a "lying UI" the PRD forbids.

critical

Double-click descend collides head-on with Excalidraw's native double-click

EXPERIENCE §Component Patterns "Work = descend"; §Interaction Primitives
In Excalidraw 0.18, double-clicking a shape enters bound-text editing. The canvas passes only onChange (line 709) and theme="dark" (line 691) — there is no double-click interception, so the default is fully in force. Binding double-click to descend means descending a module also tries to edit its label, and double-click now means "rename" on components but "descend" on modules — two conflicting meanings for one gesture, both fighting the engine. The primary "work" gesture is unimplementable without hacking Excalidraw's pointer pipeline.
Fix: pick a descend trigger the engine leaves alone (a corner "enter" control, or ⌘·/Enter-on-selected-module), state explicitly that double-click text-edit is suppressed on module symbols, and define the module-rename gesture separately.
Cross-link (converging criticals): Accessibility flags the same descend gesture has no keyboard binding at all and no screen-reader path (AX-C1 / AX-C2 / AX-H1). Engine-infeasible by mouse and unreachable by keyboard — the two criticals land on one object.
critical

Descend-as-scene-swap has no coordinate / data model

EXPERIENCE §Component Patterns; §Foundation; DESIGN §Components "Boundary pin"
Descend is specified as a scene-swap — "the canvas becomes the module's internals" — distinct from FR10 expand-in-place. But the compiler does a single flat compile of the whole spec into one scene, and the spine insists "structural data and coordinates live in the spec." A component has one coordinate in the spec, yet it must appear at one position in the full-system view and a different position in the descended module-internal view. Nowhere is it said where the module-internal-view positions live. A builder cannot compile the subscene deterministically (NFR2) without inventing a second coordinate space; putting it in the spec reintroduces exactly the PR-diff pollution OQ4 was resolved to avoid.
Fix: state that descended-view layout is derived/auto-laid-out (not stored), or that per-scope positions live in the project-folder config; specify subscene extraction + synthetic boundary-pin generation as an explicit build dependency.
high

Boundary pins "docked to the canvas edge" fight the infinite canvas

DESIGN §Components "Boundary pin"; EXPERIENCE §Component Patterns / §View switcher
Excalidraw is an infinite pan/zoom surface — there is no fixed "canvas edge" in scene space. An element pinned "at the edge" as a real Excalidraw element scrolls away when you pan; as a screen-fixed DOM overlay it cannot be the endpoint of a native Excalidraw arrow. So "connections from outside enter via boundary pins at the edge" is physics the engine does not offer.
Fix: decide the pin model explicitly — scene-space pins placed at the subscene's computed bounding box (they pan with content) vs. an overlay "gutter" with non-Excalidraw connector rendering — and write it into the spine.
high

Line-jump, line-highlight, syntax coloring, and line numbers require replacing the textarea — an unflagged major dependency

DESIGN §Components "Editor"; EXPERIENCE §Editor / §Interaction Primitives
The editor is a plain <textarea id="spec-textarea"> (editor-panel.tsx:136) with no line numbers and no per-line styling. The DESIGN editor token promises line numbers, syntax-* YAML coloring, and an accent-dim line-highlight; EXPERIENCE makes bidirectional line-jump an MVP, "named critical." A <textarea> cannot render line-highlight backgrounds, syntax colors, or a gutter — every one needs CodeMirror/Monaco. The single most-promised interaction silently depends on ripping out and replacing the editor, which no artifact flags as scope.
Fix: name the code-editor swap as an explicit MVP dependency (or descope syntax/line-highlight to what a textarea overlay can fake), so the estimate isn't a surprise.

Accessibility review — accessibility auditor

review-accessibility.md 2 critical · 6 high · 8 medium · 5 low

The spines are genuinely strong where they legislate: the color-never-sole-carrier contract for type and severity holds, the 13px density correction is real, prefers-reduced-motion is named, and every declared WCAG-AA floor combination computes clean. But the canvas — the product's right half — has no stated keyboard navigation and no stated screen-reader position, so a keyboard-only or blind architect has no committed path to select, peek, descend, or perceive a single node; the editor is a perfect accessible equivalent yet the spine never says so. Secondary but real: the command palette is claimed as "keyboard entry to everything" with no command inventory, several interactive states have no stated focus or non-color differentiation, and a handful of load-bearing token pairs the floor never fenced miss AA by a hair.

critical

Canvas has no committed keyboard navigation

EXPERIENCE §Component Patterns / Interaction Primitives
Every canvas gesture is mouse-defined. The keyboard map binds only Esc (ascend/dismiss) and Space (peek an already-selected module) — nothing selects or moves between nodes, and nothing descends. The entire tiered-navigation model (peek / descend / expand-in-place), the core of the product, is unreachable without a mouse. The Accessibility Floor promises reachability for summoned surfaces but conspicuously omits the canvas itself. Excalidraw's own keyboard support for traversing scene objects is limited, so this cannot be assumed — it must be designed or honestly punted.
Fix: add a canvas keyboard model — Tab/arrows move a focus ring between nodes/pins in reading order; Enter descends, Space peeks, Esc ascends; a "Go to node…" palette command jumps focus by name. If a full spatial model is out of MVP scope, state that explicitly and route keyboard users to the editor + "Go to node."
Cross-link (converging criticals): Adversarial shows the mouse descend gesture is itself engine-infeasible (double-click collides with Excalidraw's native double-click). Engine-broken by mouse and unreachable by keyboard — one object, two criticals.
critical

No screen-reader / accessible-equivalent position for the canvas

DESIGN §Components; EXPERIENCE §Foundation, Accessibility Floor
The canvas is an inherently visual Excalidraw surface, and the spines say nothing about how a screen-reader user perceives it: no aria-label on the canvas region, no roles/labels for nodes, chips, badges, or pins, and no stated position that the YAML editor is the accessible textual equivalent of the diagram. This is the one place the product is unusually well-positioned — the editor is the honest contract — yet the commitment is absent, so it will not be built or QA'd. Silence here = a blind user gets an unlabeled canvas and nothing else.
Fix: state in the Accessibility Floor that "the canvas is a supplementary visual view; the editor is the screen-reader-accessible equivalent and carries the full contract," aria-label the canvas region, and expose node names/roles where Excalidraw permits. Add live-region announcements for diagnostics count, sync-health state, save/dirty state, and simulation start/stop.
high

Descend has no keyboard binding — hierarchy navigation is one-way

EXPERIENCE §Interaction Primitives
Esc ascends one level (stated), but the only descend gesture is double-click. A keyboard user who somehow reaches a module can climb out of the hierarchy but never in — the VHDL descend/ascend pillar, the admired anchor, is half-reachable.
Fix: bind descend to Enter (or double-Enter) on a focused/selected module, add a "Descend into module" palette command, and mirror Esc↔descend in the keyboard map so the pair is symmetric.
Cross-link: subset of AX-C1 (canvas keyboard nav); and Adversarial shows the double-click descend is engine-broken even for mouse.
high

"Keyboard entry to everything" is claimed but not backed by a command inventory

EXPERIENCE §IA table, Command palette
The IA calls the command palette "keyboard entry to everything," but no command inventory is committed, and the spatial/canvas operations a mouse user performs — select node X, descend into Y, expand-in-place, toggle a type's visibility, switch view, resolve a specific drift, run a quick-fix, insert a template, run/pause/step the sim, dock the drawer, export — are nowhere enumerated as commands. An "everything" claim with no backing list is a lying-UI risk against the spine's own "zero lying UI" rule.
Fix: add a Command Inventory listing (or ruling in-scope) every mouse-reachable action as a palette command, especially the canvas-spatial ones; commit that the palette is exhaustive, or narrow the claim.
Cross-link: Adversarial's first-timer discovery gap (A §2) is the same summon vocabulary with nothing to teach it.
high

Conflict prompt (data-loss modal) has no stated focus management

EXPERIENCE §Conflict prompt, State Patterns
The conflict prompt — "Changed on disk. Reload or keep your edits?" — is the common case, and one choice overwrites disk while the other discards the buffer: irreversible either way. Yet nothing is stated about focus trap, initial focus, default/destructive-button distinction, or Esc behavior (and here Esc is dangerous — it must not silently pick a data-losing default). A keyboard user could destroy work by hitting the wrong key.
Fix: modal traps focus, initial focus lands on the non-destructive choice, both buttons are keyboard-operable and labeled distinctly (not color-only), Esc cancels to the safe state (keep-editing, no write), and focus restores to the editor on close.
Cross-link: Adversarial flags the same common-case event has no precedence when the modal + data-loss toast + drift chip fire together (A §5).
high

Toasts — including the data-loss warning — not committed to a live region or keyboard-reachable action

DESIGN §Toast; EXPERIENCE §Sync-health chip + data-loss toast
The data-loss toast fires when canvas content would vanish on reload — a genuine loss warning — and export toasts carry an open/download action. Nothing states the toast is announced via aria-live, whether it steals focus, or that its action link is keyboard-focusable and Esc-dismissible. A screen-reader or keyboard user silently misses the loss warning and cannot reach "Undo/open."
Fix: render loss warnings in an aria-live="assertive" region (polite for completions), do not steal focus, keep action + dismiss keyboard-reachable while visible, and mirror the loss warning as a diagnostics/sync entry so it survives toast timeout.
Cross-link: pairs with AX-H3 and Adversarial A §5 on the same conflict/data-loss common-case event.
high

Selection ring, error border, and simulation glow stack on one node, distinguished by color/glow alone

DESIGN §Component node; EXPERIENCE §Canvas display elements
A node can be simultaneously selected (accent ring), erroring (danger border), and on an active sim path (accent glow). Selection ring and simulation glow are the same hue, so a selected node on a sim path is ambiguous; error vs the others is a pure color swap. No shape/icon/stroke-style differentiation is stated — this reintroduces color-as-sole-carrier for node state (solved only for type and severity).
Fix: differentiate by more than color — selection = solid ring + handles, error = dashed danger border + an error glyph, simulation = animated/pulsing glow + a "live" readout — and define the stacking order for co-occurrence in DESIGN §Component node.
Cross-link: Adversarial's "four look-alike status dots at rest" (A §2) is the same color-as-sole-carrier problem for chrome-level signifiers.
high

Load-bearing token pairs the contrast floor never fenced miss WCAG AA

DESIGN §Colors "Contrast floor", Components
The declared floor combinations all pass, but three undeclared load-bearing pairs fail: danger on danger-dim = 4.23:1 (error diagnostic-badge glyph+count — the single most important severity has the only failing badge); accent on accent-dim = 4.18:1 (the open file's name in the file rail — the indicator of which file you are editing); syntax-punctuation on background = 3.01:1 (YAML structural punctuation a low-vision author must read to parse structure).
Fix: brighten danger toward ~#ef6d70 (or darken danger-dim) to ≥4.5 on the fill; use foreground not accent for the active filename + an accent marker; raise syntax-punctuation (e.g. #7a7972+) or declare it decorative; add all three to the DESIGN contrast-floor list.
Cross-link: the rubric flagged button-primary as similarly unfenced (Token completeness, low) — but the auditor computed btn-primary-fg/accent = 5.70:1 (PASS), so that one clears AA; these three do not.
medium

13px floor contradicts the spine's own typography tokens

DESIGN §Typography; EXPERIENCE §Accessibility Floor
The floor says interactive/content text is ≥13px (only eyebrow at 11px), but caption (12px), readout (12px — "ids and metrics — latency, throughput, packet counts"), and kbd (11px) all carry content, re-importing the 9–11px squint problem §7 called out.
Fix: raise readout/caption to 13px and kbd to ≥12px, or amend the floor to carve them out and justify each — but readout carrying metrics is hard to justify as non-content. Recommend raising readout.
medium

Focus is not stated to move on selection (drawer) or after descend

EXPERIENCE §Detail drawer, Module symbol
"Selecting any unit opens the detail drawer," but nothing says focus moves into the drawer's first field — so a keyboard user opens a form they must then hunt for. Likewise, after descend the canvas focus target inside the module is unstated.
Fix: state that selection moves focus to the drawer's first field (or a documented ⌘J/Tab path into it), and that descend places focus on the first boundary pin or node of the entered module.
medium

Expand-in-place has no stated keyboard path

EXPERIENCE §Module symbol
Expand-in-place is triggered by "an explicit corner control or context-menu action." Corner controls need focus (unstated) and context menus need a keyboard opener (Menu/Shift+F10, unstated).
Fix: bind expand-in-place to a key on a focused module and/or a palette command; ensure the context menu opens from the keyboard.
medium

Sync-health chip resolution has no stated keyboard operation

EXPERIENCE §Sync-health chip
The chip "click expands a popover of per-drift resolve actions," and drifts can risk data loss. The chip isn't in the Accessibility Floor reachability list, and popover keyboard operation (focus, arrow, Esc) is unstated.
Fix: add the sync-health chip to the reachable set; specify focus into the popover, arrow-through per-drift actions, and Esc to close.
medium

Playback bar / simulation transport not committed to keyboard; reduced-motion coupling is vague

EXPERIENCE §State Patterns "Simulation running", Interaction Primitives
The playback bar (speed, pause, step) is absent from the reachability commitment, so a keyboard user may be unable to pause or step a running simulation — the app's largest continuous motion. prefers-reduced-motion is named generally but not explicitly tied to the moving packet-dot animation.
Fix: add playback controls to the reachable set with keys (e.g. K pause/play, ,/. step); state that prefers-reduced-motion suppresses the simulation packet motion and that simulation is pausable (WCAG 2.2.2).
medium

Browser zoom / text-resize (WCAG 1.4.4 / 1.4.10 reflow) not addressed

DESIGN §Layout & Spacing; EXPERIENCE §Responsive & Platform
"Desktop-only," fixed two-pane, "narrow windows degrade gracefully — not designed." Reflow at 200% zoom and text resize to 200% are AA requirements even for desktop web; the non-responsive stance may break layout at zoom with no committed behavior. (Canvas ⇧1 fit is diagram zoom, not UI text zoom.)
Fix: commit a minimum — UI text scales/reflows to 200% without loss of content or function within the desktop frame (panes may narrow to minimums, chrome may collapse), even without a full responsive layout.
Cross-link: Adversarial's 1024px pane-arithmetic + no-hide-order gap (A §5) is the same responsive stance underspecified.
medium

Roving/arrow-key navigation committed only for tabs + view switcher, not the palette or diagnostics lists

EXPERIENCE §Accessibility Floor
Roving tab focus is promised for tab bars and the view switcher, but the command-palette result list and the expanded diagnostics list are vertical option lists that equally need arrow-key nav with a single tab stop — unstated. Also: the view switcher is a "dropdown" in DESIGN/Component Patterns but a roving "tab bar" in the Floor — different ARIA patterns (combobox/listbox vs tablist).
Fix: extend the arrow-key/single-tab-stop commitment to the palette list and diagnostics list; reconcile the view-switcher description (dropdown or tablist) so the keyboard pattern is unambiguous.
medium

Dirty-dot and low-value contrast edges

DESIGN §Status bar, Colors
The dirty state is an accent dot only, with no text affordance — small and color/presence-only; a low-vision user may miss "unsaved." Separately, accent-strong on surface = 3.61:1 (status-bar accent): fine as a graphical accent (≥3:1) but fails 4.5:1 if it ever carries text.
Fix: pair the dirty dot with a text/tooltip affordance ("Unsaved") or a filename style change; fence accent-strong to non-text use, or don't use it for status-bar labels.
low

foreground-dim fails 4.5:1 on every surface — protected by declaration, but two edge cases lean load-bearing

DESIGN §Colors
Scoped as "decorative/supplementary only… never sole carrier of essential meaning," so its 2.99–3.66:1 ratios are compliant by contract. Two uses press that boundary: editor line numbers (the line-jump feature navigates by line) and the disabled future view-switcher entries (2.99:1 on surface-elevated).
Fix: keep them supplementary; ensure line-jump never requires reading a dim number.
low

Peek dismissal focus-return not stated

EXPERIENCE §Module symbol
Esc dismisses the peek card, but where focus returns (should be the peeked module) is unstated.
Fix: state focus returns to the module that was peeked.
low

High-speed simulation (up to 5×) vs. flash thresholds not addressed

EXPERIENCE §State Patterns; extract §3
The build offers 0.5×–5× playback with moving packet dots; at high speed, rapidly appearing dots could approach WCAG 2.3.1's three-flashes-per-second limit. The spines don't address it.
Fix: state that packet animation never exceeds the flash threshold at any speed (cap effective flash rate or use motion, not blink).
low

Border hairlines sit far below 3:1 — by design, worth an explicit note

DESIGN §Elevation & Depth, Colors
border on surface/background = 1.18–1.28:1 and border-node/border-pin = 1.36–1.61:1 — intended to "nearly vanish," so not text/essential graphics. But module symbols (no type tint) rely on border-node = 1.49:1 against the canvas plus a ~1.1:1 fill delta — their boundary is nearly imperceptible for low-vision users, and the object-boundary is essential for an untyped module box.
Fix: ensure module symbols carry a perceivable boundary (raise border-node toward 3:1 against surface-canvas, or add a shade/tint).
low

Layers visibility control and "operable" claims are asserted, not specified

EXPERIENCE §IA, Accessibility Floor
"View switcher, layers control, library palette, and diagnostics are all reachable and operable without a mouse" is a blanket assertion with no per-control keyboard spec (how a toggle flips, how a library item is inserted — though the editor "Insert template" path covers library insertion honestly).
Fix: note the concrete key/mechanism for each (Layers toggle = Space/Enter on a focused row; library = editor "Insert template" as the committed keyboard equivalent).
